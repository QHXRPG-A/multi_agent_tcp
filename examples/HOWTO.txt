multi_agent_tcp — Peer agent CLI communication bus
==================================================

Project pivot (2026-04-30): the framework is no longer framed as "Cursor /
CodeMaker as upstream orchestrator + N CodeMaker workers". It is now
positioned as a peer-to-peer agent CLI communication bus: any agent CLI
(CodeMaker / Claude Code / Codex / custom) or external script can connect
to a shared broker and act as both receiver and initiator. CodeMaker is
currently the only fully-supported CLI adapter; Claude Code / Codex
This file documents the existing broker / agent / cluster / orchestrate
primitives, all of which work the same as before -- only the narrative
changed. Commands and config are unchanged.

Quick Start with CLIWorkerBackend (recommended initiator entrypoint)
--------------------------------------------------------------------

CLIWorkerBackend is one convenient initiator-side entrypoint: it manages a
broker plus N agent processes for you. Today the agent processes are
CodeMaker workers; once additional CLI adapters land, other CLIs will be
selectable through the same class.

Python API — parallel tasks (returns ParallelResult):

    from pathlib import Path
    from multi_agent_tcp import CLIWorkerBackend, WorkerConfig

    async def main():
        async with await CLIWorkerBackend.create(
            workers=[
                WorkerConfig("cm1", cwd=Path("F:/src")),
                WorkerConfig("cm2", cwd=Path("F:/src")),
                WorkerConfig("cm3", cwd=Path("F:/src")),
            ],
            port=9140,
        ) as cluster:
            result = await cluster.run_parallel([
                ("cm1", {"prompt": "Task A ..."}),
                ("cm2", {"prompt": "Task B ..."}),
                ("cm3", {"prompt": "Task C ..."}),
            ])
            # Structured access:
            for wr in result.succeeded:
                print(wr.worker, wr.status, wr.answer[:200])
            for wr in result.failed:
                print(wr.worker, wr.status, wr.stderr[:200])
            print(result.summary)        # human-readable for LLMs
            print(result.ok)             # True if all succeeded
            print(result.to_dict())      # LLM-friendly (status + answer only)
            print(result.to_raw_dict())  # debug (includes raw_stdout/stderr/elapsed)

    import asyncio; asyncio.run(main())

Python API — fan-out + reduce (parallel search then merge):

    result = await cluster.run_parallel_reduce(
        tasks=[
            ("cm1", {"prompt": "Search module A interfaces"}),
            ("cm2", {"prompt": "Search module B interfaces"}),
            ("cm3", {"prompt": "Search module C interfaces"}),
        ],
        reduce_worker="cm1",
        reduce_prompt="Merge and deduplicate:\n{results}",
    )
    print(result.answer)      # merged answer from reduce worker
    print(result.parallel)    # ParallelResult from fan-out phase
    print(result.ok)          # True if reduce step succeeded

Python API — serial chain (structured context injection):

    results = await cluster.run_chain([
        ("cm1", {"prompt": "Step 1 ..."}),
        ("cm2", {"prompt": "Step 2, continue from previous ..."}),
        ("cm3", {"prompt": "Step 3, wrap up ..."}),
    ])
    # Each step receives context as:
    #   body["context"] = {"worker": "cm1", "status": "success", "answer": "..."}

Python API — connect to an already-running cluster:

    cluster = await CLIWorkerBackend.connect(port=9140)
    result = await cluster.run_parallel(tasks)
    await cluster.close()

CLI — one-shot (start cluster, run tasks, stop):

    python -m multi_agent_tcp run-parallel --config cluster.json --tasks tasks.json -o result.json
    python -m multi_agent_tcp run-parallel-reduce --config cluster.json --tasks tasks.json --reduce-worker cm1 --reduce-prompt "Merge:\n{results}" -o result.json
    python -m multi_agent_tcp run-chain --config cluster.json --tasks tasks.json -o result.json

CLI — persistent cluster:

    # Terminal 1: start cluster (foreground, Ctrl+C to stop)
    python -m multi_agent_tcp cluster start --config multi_agent_tcp/examples/cluster.json

    # Terminal 2: submit tasks to running cluster
    python -m multi_agent_tcp run-parallel --port 9140 --tasks multi_agent_tcp/examples/tasks_parallel.json

Config files:
  cluster.json: { host, port, workers: [{ agent_id, cwd, model?, timeout_sec? }] }
  tasks.json:   [{ to: "cm1", body: { prompt: "..." } }, ...]

See examples/cluster.json, examples/tasks_parallel.json, examples/tasks_chain.json.


Low-level components
--------------------

1) Start broker (one terminal), from repo root f:\src\Package\Script\Python:

   python -m multi_agent_tcp broker --config multi_agent_tcp/examples/broker.json

   Or without file:

   python -m multi_agent_tcp broker --host 127.0.0.1 --port 9123

   broker.json fields:
   - host: bind address (default 127.0.0.1)
   - port: TCP port (default 9123)

2) Start each agent in its own process (separate terminals):

   python -m multi_agent_tcp agent --config multi_agent_tcp/examples/agent_echo.json

   agent JSON fields:
   - agent_id: unique name on this broker (required)
   - broker_host, broker_port: where the broker listens (required unless nested broker below)
   - broker: optional object { "host", "port" } as alternative to broker_host/broker_port
   - role: optional string, stored in register message for your own logic
   - mode: optional "echo" | "listen" | "codemaker-worker" — CLI --mode only used if JSON omits mode

   CLI:
   python -m multi_agent_tcp agent --config <path> [--mode echo|listen|codemaker-worker] [-v]

3) Spawn several agents from one JSON (Windows opens new consoles per child):

   python -m multi_agent_tcp spawn --config multi_agent_tcp/examples/spawn_two_echo.json

   spawn JSON fields:
   - broker_host, broker_port: broker address for all children
   - agents: list of { agent_id, role?, mode?, codemaker? }  (pass through "codemaker" for codemaker-worker)
   - python: optional path to interpreter (default: current sys.executable)

4) Library usage (same process / tests):

   from multi_agent_tcp.client import AgentTCPClient
   import asyncio

   async def demo():
       c = AgentTCPClient("my", "127.0.0.1", 9123, role="worker")
       await c.connect()
       await c.send_to("other_id", {"text": "hi"})
       async for m in c.incoming():
           print(m)

5) Protocol: length-prefixed JSON frames over TCP.
   Client -> broker: register | send | broadcast | ping | batch_gather
   Broker -> client: registered | message | broadcast | error | pong | gather_result

   batch_gather (peer-to-peer fan-out primitive): one RPC issued by any initiator
   (an external Python script, a CI job, or another agent CLI calling out via its
   bash tool) to deliver different bodies to many peer agents and wait until every
   distinct target has replied with gather_reply, then receive a single
   gather_result on the same connection.

   Initiator -> broker::

     { "type": "batch_gather", "id": "<unique_str>", "timeout_sec": 300,
       "items": [ { "to": "<agent_id>", "body": <json> }, ... ] }

   If any target is offline, the broker responds with gather_result ok:false (code
   pre_check_failed) and sends no per-target messages. Duplicate id while a gather is
   in flight: gather_result ok:false code duplicate_gather_id.

   Broker -> each target (normal message frame plus gather metadata)::

     { "type": "message", "from": "<initiator_id>", "body": <json>,
       "gather": { "id": "<same as batch_gather.id>", "reply_to": "<initiator_id>" } }

   Target -> broker (extend send; backward compatible)::

     { "type": "send", "to": "<reply_to / initiator>", "body": <json>,
       "gather_reply": "<same id>" }

   Agents that ignore gather_reply will not complete the gather (timeout). Built-in
   echo and codemaker-worker modes pass gather_reply when the inbound message has gather.

   Broker -> initiator when all expected targets have replied (or failure)::

     { "type": "gather_result", "id": "<id>", "ok": true|false,
       "replies": { "<agent_id>": { "body": <their send body> }, ... },
       "errors": { "<agent_id>": { "code": "<code>", "message": "<text>" }, ... },
       "code": "<optional top-level reason>", "message": "<optional detail>" }

   Common errors.codes: pre_check_failed, duplicate_gather_id, timeout, dispatch_failed,
   target_disconnected. Per-target errors use the same code strings where applicable.

   Library: AgentTCPClient.batch_gather(gather_id, [(to, body), ...], timeout_sec=...)
   routes gather_result to the waiting coroutine; other frames still go to incoming().

Run smoke test (broker must be running):
   python -m multi_agent_tcp.smoke_local

6) Orchestrate client (connect broker, send / wait / broadcast from JSON)

   Broker and target agents must already be running.

   python -m multi_agent_tcp.orchestrate --recipe multi_agent_tcp/examples/recipe_chain.json

   Recipe fields:
   - broker_host, broker_port (or nested broker), self_id, role (optional)
   - steps: ordered list; each step is exactly one of:
     * { "send_to": "<agent_id>", "body": <json> }  OR  { "send_to": "...", "body_file": "relative.json" }
     * { "broadcast": { "body": ..., "exclude_self": true } }  OR body_file inside broadcast
     * { "wait_for": { "from": "<agent_id>|omit", "timeout_sec": 300, "accept_broadcast": false } }
     * { "batch_gather": { "id": "<optional; random if omitted>", "timeout_sec": 300,
         "items": [ { "to": "<agent_id>", "body": <json> }, ... ] } }
       items entries may use "body_file" instead of "body" (path relative to recipe dir).

   Example (requires broker + echo agents alpha and beta, e.g. spawn_two_echo.json):

     python -m multi_agent_tcp.orchestrate --recipe multi_agent_tcp/examples/recipe_batch_gather.json

   Programmatic: AgentTCPClient.batch_gather(...) or send_to(..., gather_reply=...) after
   reading gather.id from an inbound message.

7) Three CodeMaker workers + relay demo (one command)

   From f:\src\Package\Script\Python (or pass --cwd to your repo root):

   python -m multi_agent_tcp.demo_three_codemakers

   Default broker port is 9133 (not 9123). Sets MULTI_AGENT_TCP_VERBOSE=1 to show child stdout/stderr.

   Parallel search-style batch (three codemaker CLI workers + batch_gather, default port 9134):

   python -m multi_agent_tcp.demo_three_codemaker_search
   python -m multi_agent_tcp.demo_three_codemaker_search --cwd f:\src\Package\Script\Python

   gclient code-location batch (default port 9140); add ``--trace`` for stderr logs on parent
   and ``-v`` on broker/agent children. Log prefixes: ``[orch]`` orchestrator client,
   ``[gather]`` broker batch_gather / gather_reply, ``[chain]`` codemaker-worker around
   ``codemaker_run``, ``[cil]`` codemaker subprocess spawn/exit/timeout in codemaker_bridge.

   python -m multi_agent_tcp.demo_gclient_three_search --trace

   Manual equivalent: start broker on 9133, then
   python -m multi_agent_tcp spawn --config multi_agent_tcp/examples/spawn_three_codemaker.json
   (run spawn from the directory you want as codemaker cwd, or edit JSON "cwd" to an absolute path).

8) CodeMaker CLI integration (non-interactive `codemaker run`)

   CodeMaker is not a TCP peer: run it *inside* an agent process. Mode `codemaker-worker`
   runs (per multi_agent_tcp/codemaker_cli.md):

     codemaker <base_args...> [-m <model>] "<prompt>"

   Doc highlights: `codemaker run` for non-interactive runs; `--format json` for machine
   readable output; `-m "netease-codemaker/<model>"` to set model; CI auth via
   CODEMAKER_AUTH_USER + CODEMAKER_AUTH_TOKEN or CODEMAKER_AUTH_KEY.

   Start a worker from the project directory you want CodeMaker to use (cwd):

   python -m multi_agent_tcp agent --config multi_agent_tcp/examples/agent_codemaker_worker.json

   agent_codemaker_worker.json fields under "codemaker":
   - command: executable (default "codemaker"; Windows may use full path to codemaker.exe)
   - cwd: subprocess working directory (project root; codemaker.json / opencode config as per doc)
   - model: optional; if set, `-m` and this value are inserted before the final prompt
   - base_args: argv after command, before optional -m and prompt (default ["run","--format","json"])
   - timeout_sec: optional cap in seconds for one run (omit for no limit)
   - prompt_via_file: "auto" | "always" | "never" (default auto). If auto/always, non-ASCII prompts
     are written as a UTF-8 temp file and passed with `codemaker run ... -f <path>` plus a short
     ASCII anchor message, avoiding Windows console / argv codepage issues.
   - anchor_message: optional; when using prompt_via_file, prepended to the UTF-8 file body.
   - run_stub_message: optional short ASCII first positional for `codemaker run` when using -f
     (default "Task in attachment."). CLI requires a message *and* treats args after -f as paths,
     so order is: stub message, then -f promptfile.

   TCP/JSON bodies are always UTF-8 in this framework; ensure your editor and terminal use UTF-8
   (e.g. Windows: `chcp 65001`, PowerShell 7, or set `PYTHONUTF8=1` — child processes already get
   `PYTHONUTF8=1` from codemaker_bridge).

   Send a task with AgentTCPClient.send_to:

     body: { "prompt": "instruction", "context": "optional extra text (appended after ---)" }

   Or body as a plain string. Reply shape:

     { "ok": bool, "codemaker": { "returncode", "stdout", "stderr", "timeout" }, "via": ... }

   For headless auth on servers, set env vars then start the agent (see codemaker_cli.md
   section around CODEMAKER_AUTH_USER / TOKEN / KEY).
