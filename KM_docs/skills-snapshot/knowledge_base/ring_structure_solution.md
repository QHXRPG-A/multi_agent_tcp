# 环状结构解决方案（工程版）

## 1. 定位

- 外层把环状结构视为一个普通 `agent`，不直接调度环内的回路细节。
- 环内仍由多个真实 `agent` 按顺序协作完成一次内部执行会话。
- 框架不永久改写蓝图结构，只在运行时为每个 `agent` 生成当前会话下的可达节点视图。
- 环状结构只跑一轮，顺序固定，不允许反向流转或重复回流。

## 2. 核心概念

- 环类 `agent`：外层看到的复合 `agent`，内部包含一组按环顺序排列的 `agent`。
- 内部执行会话：环类 `agent` 被触发后，在环内按固定顺序推进的一次处理过程。
- 入口消息：外部传入环内某个节点的消息。一次内部执行会话可以包含多个入口消息。
- 起始 `agent`：当前会话中按环顺序最先开始执行的内部 `agent`。
- 环审核官：当前会话的最终审核节点，通常是起始 `agent` 在环内反向的第一个 `agent`。

## 3. 会话与队列

- 一次内部执行会话不是由单条外部消息决定，而是由框架识别出的一组同会话入口消息共同决定。
- 多个入口消息如果属于同一次内部执行会话，应按环内顺序挂到对应节点，等待框架合并后继续推进。
- 当一个内部执行会话处于 active 状态时，新的独立会话进入环类 `agent` 的外层队列，按 `FIFO` 等待。
- 普通 `agent` 的外层状态仍由框架 `tick` 推进。
- 环类 `agent` 的内部协议状态由内部行为触发，但状态落账、事件记录、队列释放和外层调度切换仍由框架完成。

## 4. 流转规则

- 内部只允许沿一个方向前进，不存在信息反流。
- 一个内部执行会话中，每个内部节点最多执行一次。
- 框架根据当前会话的运转位置，动态调整环内 `agent` 的可达节点。
- 内部节点只能看到框架暴露给它的当前可达节点，不能绕过框架直接把消息发给隐藏节点。
- 审核官负责本轮最终闭环判断和最终对外输出，不再把消息发回环内节点。
- 审核官的最终可达节点只保留本轮需要统一流出的环外节点。

## 5. 可达节点视图

- 可达节点视图是运行时视图，不是蓝图结构本身。
- 同一个 `agent` 在同一会话的不同阶段，可以看到不同的可达节点。
- 如果起始 `agent` 自己还有外部链路，它可以在完成内部首跳后切换到外部可达节点。
- 起始 `agent` 切换到外部可达节点时，不审核外部传入当前会话的入口消息。
- 外部输出边不是默认全部暴露给原始源节点；框架需要判断该输出是否会导致信息在到达审核官前提前流出。
- 会导致本轮无法继续到达审核官的外部输出，应收束到审核官统一处理。

## 6. 多入点

- 多个外部来源指向同一环类结构时，不等于启动多次内部执行会话。
- 框架应先根据环顺序确定起始 `agent`。
- 指向后续节点的入口消息，应暂存在对应节点，等前序节点产出的消息到达后再合并。

示例：

```text
e -> b
f -> c
```

如果按顺序 `b` 早于 `c`，则 `b` 是起始 `agent`。`b` 处理来自 `e` 的消息后生成 `infob`，框架在推进到 `c` 前，将 `infob` 与来自 `f` 的 `infof` 合并，再转发给 `c`。

## 7. 多出点

- 多出点按当前会话的可达节点视图处理。
- 如果外部输出不会破坏内部顺序，也不会导致消息跳过审核官，可以按普通 `agent` 分发逻辑暴露给当前节点。
- 如果外部输出会导致消息在到达审核官前提前流出，则该输出不暴露给当前节点，而是收束到审核官。
- 审核官对外输出时，仍走传统 `agent` 信息分发逻辑，由框架向它暴露最终可达节点。

## 8. 案例：`e -> a -> b -> c -> d -> e`

### 原始结构

```text
外部输入 -> a
外部输入 -> e
e -> a
a -> b
b -> c
c -> d
d -> e
b -> 外部输出
c -> 外部输出
```

### 会话判定

- `外部输入 -> e` 和 `外部输入 -> a` 不必然产生两次内部执行会话。
- 在同一次触发中，它们可以被框架识别为同一会话的两个入口消息。
- 框架按环顺序选择 `e` 作为起始 `agent`。
- 指向 `a` 的入口消息先暂存在 `a`。
- `e` 处理完成并把消息传给 `a` 后，框架将 `e -> a` 的消息与暂存在 `a` 的入口消息合并，再转发给 `a`。

合并示例：

```text
外部输入 -> e
外部输入 -> a
e -> a -> b -> c -> d
```

这不是两次内部执行会话：

```text
外部输入 -> e -> a -> b -> c -> d
外部输入 -> a -> b -> c -> d
```

而是一次内部执行会话：

```text
外部输入 -> e
外部输入 -> a 暂存
e 处理后生成 info_e
框架把 info_e 和暂存在 a 的入口消息合并
a 执行一次
a -> b -> c -> d
```

`a` 收到的输入应是结构化输入，而不是简单字符串拼接：

```json
{
  "from_previous": "info_e",
  "entry_messages": [
    {
      "source": "external",
      "target": "a",
      "payload": "外部给 a 的消息"
    }
  ]
}
```

### 角色判定

- `e` 是当前会话的起始 `agent`。
- `e` 在环内反向的第一个 `agent` 是 `d`，因此 `d` 是当前会话的环审核官。
- 如果 `e` 自己也有外部链路，`e` 可以在把消息传给 `a` 之后切换到外部可达节点；但 `e` 不审核外部传入当前会话的入口消息。

### 可达节点调整

- 会话开始时，`e` 的可达点只暴露为 `a`。
- `e` 把消息传给 `a` 后，框架可以把 `e` 的可达点切换为它自己的外部节点。
- `a` 的可达点只暴露为 `b`。
- `b` 的可达点暴露为 `c`，以及框架判定为可直接外发的外部节点。
- `c` 的可达点只暴露为 `d`，不直接暴露会导致本轮提前结束的外部输出节点。
- `d` 作为审核官，最终可达点暴露为本轮需要统一流出的外部节点。

### 为什么不能让 `c` 直接流出

- 如果 `c` 直接对外流出并结束本轮，信息就无法继续到达 `d`。
- 当前规则要求本轮必须按 `e -> a -> b -> c -> d` 完整走到审核官。
- 因此 `c` 的外部输出需要收束到审核官 `d`。
- `c` 只能按环方向把消息传给 `d`，由 `d` 负责把本轮信息分发给对应的外部 `agent`。

### 执行顺序

```text
e -> a -> b -> c -> d
```

- `b` 如果存在不会破坏本轮顺序的外部输出，可以按普通 `agent` 分发逻辑外发，同时继续把消息传给 `c`。
- `c` 不直接输出给会导致本轮提前结束的外部节点，只把消息传给 `d`。
- `d` 判断本轮是否闭环。
- 闭环成立后，`d` 通过框架暴露的最终可达节点，把消息分发给外部 `agent`。

## 9. 审核官输出协议

- 审核官自行判定当前会话是否满足闭环条件。
- 判定成立后，审核官通过框架接口发起最终对外输出。
- 一次内部执行会话只允许最终输出成功一次，输出必须幂等。
- 当审核官消息队列仍有积压时，框架必须阻止最终输出，继续按队列顺序把消息分发给审核官。
- 只有当环内所有 `agent` 都处于 `idle`，且审核官当前队列清空后，才允许最终输出。
- 审核官完成最终输出后，当前内部执行会话结束，框架释放环类 `agent` 去处理下一条外层队列中的独立会话。

## 10. 异常边界

- 同会话入口消息识别错误。
- 多入口消息合并顺序错误。
- 可达节点动态切换时状态未落账。
- 审核官重复调用最终输出接口。
- 审核官队列积压时错误放行最终输出。
- 队列超过上限。
- 内部执行会话超时。
- 审核官失败。
- 状态未落账前崩溃。
- 迟到消息进入已结束会话。
- 逆向边或内部回流被错误暴露。

## 11. 工程结论

- 这不是外层真正参与调度的环，而是对外普通 `agent`、对内单向顺序编排的复合 `agent`。
- 一次内部执行会话可以包含多个入口消息；入口消息需要按环内顺序合并，而不是简单地各自启动一轮。
- 框架的核心职责是生成并切换可达节点视图，保证内部顺序、最终审核和对外输出一致。
- 可靠性的关键约束是：单向、单轮次、同会话合并、单次最终输出、`FIFO` 外层队列、框架持有状态权威。
